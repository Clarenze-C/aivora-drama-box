Version 1, 31 October 2026 local operator date. T044 implements SPEC V2-01 and V2-10 over existing PostgreSQL records and the two existing human gates. The current checkout is dirty; no commit, deployment, DNS change, real account action or public release is part of this task. T037 closes only after the same Gate 2 flow prepares current owner-supplied metadata and T047 tests a composed live-like fixture.

## Authority and data

- The current approved season and candidate intake live in the T039 records; `EpisodePack`, directing/shot manifests, wardrobe/look/sheet/reference records live in current V2 documents; jobs, events, assets, QA findings, budget, approval and platform-post records remain the durable business truth. The workbench is a read-only projection except for existing intake and Gate 1/Gate 2 commands. Do not create a second approval, shot, asset, release or cost ledger.
- Load current typed V2 documents and verify payload/content hashes. V1 records remain visible as legacy/audit and must not be counted as V2-complete. Rows outside the owner's authorized season/episode are not returned. Human session/cookie, CSRF and bearer-first refusal rules from `review/api.py` apply to every new route; private media is streamed only through the existing owner stream.
- Current migrations have no season-to-owner relation; the existing review reads list every season for any authenticated owner. Add an explicit owner link before exposing a workbench. Existing approved seasons may be linked only from a verified human approval event; unapproved legacy seasons without trustworthy provenance stay unassigned and hidden until an audited operator assignment. New owner-created intake sets owner identity at creation. Do not infer ownership from a title, account handle, first active owner, or a worker credential. Apply the same scope to existing review JSON/pages/media routes as the new workbench; fixing only the new route would leave a leak.
- A progress snapshot is computed from persisted required work for a specific plan/version. Count accepted shots and assets only from current accepted rows with exact source lineage. A failed/retried job never counts as accepted. A new required outfit/shot changes the denominator; the visible version/revision and explanation change with it. Zero known denominator or external provider internal status yields indeterminate percent, never fabricated partial progress. Costs come from budget ledger and include settled, accrued and held exposure separately.
- Production and release are independent: a complete export/QA package is production-ready only when its current gates hold; a scheduled post is not release-verified until provider readback says so. Show each step's status, accepted/required counts, blockers, retries, waits, current/next action, version, source links, cost and timestamps. No ETA without measured comparable history.

## Owner flow

1. Three-step Script Maker: story idea; genre/tone; episode count. Advanced defaults preserve original Thai fiction, 180–300 second episodes, initial destinations, rights and budget policy. Intake only creates bounded original proposals, which the existing Gate 1 approves; no direct season approval is created by the wizard.
2. Season workbench: candidate/scope and approved bible/arc, characters and secret timing, series look, asset sheets and wardrobe. Episode workbench: editorial 30-second sections, actual ≤15-second shots, each typed reference and attempt; media/QA/review; release slots and verified outcomes. A timeline step expands to evidence and explains unknown coverage, failures and rework.
3. Gate 2 retains Approve & schedule / Revise / Reject. Before existing Gate 2 approval, the owner supplies current metadata policy and metadata for every current release slot. The same form/API calls `ReviewService.prepare_release_approval_manifest` and shows its exact hash and metadata alongside the current package. The owner then performs the existing Gate 2 action. Stale package, policy, capability or slot metadata blocks; a server may not synthesize owner metadata or use mock fallback in a live-like route. Revision returns to the same gate.
