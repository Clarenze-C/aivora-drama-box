## (a) Architecture verdict — does the accumulated finding set change the Stage 5 verdict?

The one Stage 7 Blocker, correctly rated for its instance, is here revealed as the visible edge of that single systemic defect.

Two clusters reveal a systemic/altitude problem the individual reviewers each saw only a slice of. First, the frozen-contract extension defect (Finding 1): the step keys, the Approve target carrier, the Revise target kinds, the `edit_tier` command, and even the dangling "A2 §5.2" citations share one root cause — B extends frozen vocabularies by invention with no delta protocol — and the remedy is one register plus one rule, not four patches. No scope creep beyond these: the extension builder's placement in B is master-assigned (§15 row B plus A1 OQ-1), and the B-T2 consumer enumeration is only a Nit-level overreach already reported.

Three things remain missing at top level after applying every earlier mitigation, each invisible to a single-lens reviewer: (1) B's rows of the family command table — a master-mandated (§2.2) component whose absence is the common cause of the `edit_tier` finding (Finding 3); (2) the prompt set as an owned, versioned, manifest-registered artifact — the phase's actual quality instrument, pinned by §7's own rules yet homeless in §10/§11 (Finding 4); (3) pre-approval regeneration resume semantics — the failure domain and operator capability for a half-regenerated season, which master §12.6 covers only post-approval (Finding 5). With those added and the two systemic clusters resolved through the existing guardian/migration mechanisms, the architecture itself needs no change.

## (b) Findings (Blockers → Majors → Nits)

### 1. The frozen-contract seam is one systemic defect, not four: B invents vocabulary that A1/A2's enforced contracts reject, and no enumerated contract-delta deliverable exists — Severity: 🔴 Blocker

* **Anchor:** §1.3 (lines 61–62), §3.3 (line 233), §4.2 (lines 269–275), §5.3 (line 345), §2 (line 107); §10 B1 row (line 493).
* **Finding:** Stage 5 called this residue "seam closure"; Stage 7 found four instances (step keys; Approve target kind; Revise note targets; `edit_tier`). Read together they are one root cause: B was drafted against the master, treating A1/A2's contracts as open vocabularies, while A1/A2 then froze enums, SQL CHECKs and validators with no extension protocol — and B's build plan nowhere enumerates the guardian-owned contract changes it requires.
* **Evidence (each verified first-hand):** (a) A2 note §2.2 fixes `budget_steps.step_key` by CHECK to exactly `step_01..step_10, launch, episode_production`, and `md_reservation_step_rules` requires a reservation's step_key to reference an existing `budget_steps` row of the right account kind — B's `script_maker`/`bible`/`episodes` (§1.3) fail both. (b) A1 note §4 defines `RevisionTargetKind` as exactly EPISODE|CHARACTER|VOICE|REFERENCE|STORY_UNIT|NOTE with `RevisionNoteTarget.id: UUID`, and `V3DecisionCommand` has no target field at all — B's `Approve target = {kind: proposal, id}` (§3.3) has no carrier and no kind; `SeasonProposalV3.proposal_id` ("stable per round slot", §2 line 107) is untyped and, if a slot string, cannot be the UUID A1 requires. (c) B's Revise targets `episode:<n>`, bible sections, the seam, tiers (§5.3) fit none of the six kinds (no episode UUID exists pre-STORY-LOCK, §2.1; `character_key` is a string). (d) `edit_tier` appears in no command-table row, while the family's own convention is that every phase adds its rows in A1 §6's format (A2 note §7 "A2 rows; A1 §6 columns"; A3 note §6) — A1 §6 even allocates `create_extension` to B, showing the mechanism exists and was simply not used. The only B deliverable that could carry these deltas, §10's B1 "contract bump", does not name a single A1/A2 amendment.
* **Why it matters:** each instance is discovered only at build or enforcement time, against a frozen artifact, requiring guardian-approved changes to documents B does not own. Individually text-fixable; systemically it is a structural gap in how B is scoped.
* **Recommended action:** add a "B contract deltas" register as a first-class B1 deliverable (critiqued first, per §10's own B1/B5 rule): (1) the step-key mapping decision — adopt `step_01..step_03` per A2's OQ-2 mapping, or record a new migration amending A2's CHECK; (2) `RevisionTargetKind`/`V3DecisionCommand` extension or a B-side binding-unit encoding for proposal/pack/bible-section/seam/tier targets, with the enum migration; (3) an A1-§6-format command-table row for `edit_tier` (and see Finding 3); (4) one citation convention for A1/A2/A3 notes vs phase-A-spec (fixes M-9, B-1's false pointer). Rule going forward: any B-side identifier that crosses an A-phase contract must be checked against that contract's enforced vocabulary before the B1 note is accepted.

### 2. Orchestration model gap: three of B's flows need fan-out/fan-in choreography that no phase in the family defines, and B's prose writes them as synchronous sequences — Severity: 🟡 Major

* **Anchor:** §5.2 steps 3–4 (lines 328–335), §5.1 success clause (lines 316–317), §5.3 Revise row (line 345), §4.2 (lines 266–275), §7 job table (lines 419–425).
* **Finding:** M-2 (promote_profile join), zoom-out #2 (semantic-key collision) and M-6 (repair cascade) are three symptoms of one altitude problem: B is the first phase whose job graph is not a linear chain, and the family's runtime has no join primitive — A0 §5 defines a single job with WaitExternal/Deferred/reconcile; A1's 0031 adds `logical_work_id`/`replaces_job_id`/`track_waits`; A3 adds fence/cancel/lanes. Nothing anywhere lets a job wait for N jobs and continue.
* **Evidence:** (a) §5.2's "Then: 1. tier promotion; 2. the demand list; 3. `StoryLockBindingV3`; 4. `open_gate`; 5. `BIBLE → PLANNED`" is written as one actor's consecutive steps, but §4.2/§7 make promotion N async `promote_profile` jobs whose outputs feed the demand list (tier, identity coverage) and the binding hash (tier table) — and §1.7's own invariant ("a gate is never open while that step's jobs are queued or running") makes the wait mandatory with no waiter defined. (b) §5.2 step 3's repair rounds re-plan a subset ("the earliest named episode and every later episode whose continuity input changed"), but §5.1's chain rule ("enqueue `plan_episode(n+1)`, or, after the last episode, `story_v3.season_critic`") covers only the full-chain case — for a subset, who detects completion and re-runs the critic is unstated. (c) §5.3's Revise (noted packs plus a scoped bible call, then closure revalidation, then the season critic, then gate reopen) is the same shape again. (d) B never once uses A1's `replaces_job_id` mechanism, which exists precisely for legitimate re-plans outside `jobs.semantic_key` (zoom-out #2's collision). (e) `edit_tier` (§4.2) "re-runs the season critic's deterministic checks" synchronously inside a human command, a fourth ad-hoc choreography.
* **Why it matters:** each builder's invention of the choreography lands differently, and the gate-opening invariant (§1.7) can be violated silently.
* **Recommended action:** define one continuation idiom once in §7 — e.g. the last job of a logical round (by `logical_work_id` prefix per round) enqueues the continuation job, with per-round logical work IDs and `replaces_job_id` chains — and apply it uniformly to the promote join, the repair rounds, and the Revise loop. Uses only existing A1 primitives; no new infrastructure.

### 3. Missing top-level component: B's rows of the family command table (master §2.2 mandate unmet) — Severity: 🟡 Major

* **Anchor:** document level; §3.1, §4.2, §8; master SPEC-v3.md §2.2 (lines 152–153).
* **Finding:** after applying every earlier mitigation, a master-mandated component is still absent. Master §2.2: "Each phase spec gives a command table: command, allowed states, prerequisites, the transaction (locks in the shared order), events, jobs, and the replay result." A2 note §7 and A3 note §6 supply their rows; phase-B-spec.md contains the word "command" twice (lines 10, 34) and no table. M-5 caught one casualty (`edit_tier`); the missing section is the cause.
* **Evidence:** B owns at least three human-facing commands outside the two gate decisions: `submit_v3_intake` (§3.1 — has an idempotency key but no lock order/events/replay row), `edit_tier` (§4.2 — nowhere in the family inventory), and `create_extension` activation (§8 — allocated to B in A1 §6's table, but B never supplies its row: locks, expected revision, events, replay result). The decision tables in §3.3/§5.3 are gate-handler tables, not the command table the master requires.
* **Recommended action:** add a "B commands" section with A1-§6-format rows for the three commands above (or explicitly delegate the rows to the B1/B5 notes, naming that in §10 so the critique gate checks them).

### 4. Missing top-level component: the prompt set has no owner, no package, and no acceptance hook — Severity: 🟡 Major

* **Anchor:** §7 (lines 427–431), §10 package table (lines 491–498), §11.
* **Finding:** §7 requires every `FrozenLlmCall` to carry "a pinned prompt ID and its sha256 (a prompt manifest, as `PromptManifest`, `S/contracts/v2.py:773`)" — but B needs at least six distinct non-trivial prompts (proposal §3.2, bible §4.1, architect and translation §5.1, critics §4.1/§5.2, promoted-profile §4.2), and no B package builds, versions or registers them. B-T tests exercise logic through fake adapters with scenario scripts, so prompt absence never fails acceptance. Yet master §11's pilot P0 ("representative full-season planning… 24 episodes") and the "frozen-workload LLM comparison" presuppose these prompts exist and are frozen, and the Joey-method fidelity (joey-digest.md; licence constraint master §18) lives entirely in prompt content.
* **Evidence:** §10's B1–B6 rows list records, stores, handlers, jobs and tabs — no prompt artifact; grep of the target confirms "prompt" appears only in the §7 FrozenLlmCall bullets. The reusable shape exists (`PromptManifest`); the deliverable does not.
* **Recommended action:** name the prompt set and its manifest registration in the owning package rows (B2/B3/B4/B5), and add one acceptance line (every `FrozenLlmCall` in tests references a manifest-registered prompt; the manifest ships with the package). Cheap, not speculative — the pins in §7 cannot be honored without it.

### 5. Failure domain still open after the proposed mitigations: resume semantics for a partially regenerated season — Severity: 🟡 Major

* **Anchor:** §5.2 step 3 and the CRITICAL-remains clause (lines 328–338), §5.5 (lines 375–384), §3.2's BLOCKED/retry pattern (line 222), §9 "blocked" state.
* **Finding:** M-6's cap/checkpoint and M-2's join fix breadth and choreography, but neither defines what happens when a regeneration round stalls or dies partway: quota windows (5-hour, `QUOTA_5H` in A1's `track_waits`; max-concurrent 1) or a terminal job failure leaves a mixed-version pack set — some episodes regenerated, others stale relative to the new continuity. B never states what the operator's retry action re-runs (the failed job only? the whole round? from the earliest regenerated episode?), whether a resumed round reuses completed packs, or what tab 3 displays mid-round. Master §12.6 defines exactly this closure for post-approval amendments (invalidate, fence, rebuild); B's pre-approval analogue is undefined.
* **Evidence:** §5.1's crash-and-replay clause covers a single call/episode, not a round; the fence (§7, `expected_content_revision`) quarantines stale results but quarantining is not a resume policy; §4.3's "IDs stable across revisions" makes partial reuse possible but nothing says it is intended.
* **Recommended action:** one paragraph in §5.2/§5.5: rounds are the unit of retry (idempotent via the round-scoped logical work IDs of Finding 2), completed packs in a round are kept (stable IDs make this safe), and the screen labels per-pack version status during a round.

### 6. Fold the skeleton repairs into one B1/B5 gate checklist — Severity: 🟢 Nit
