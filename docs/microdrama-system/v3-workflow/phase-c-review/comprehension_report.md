**What this proposes**

Phase C builds the fourth tab of the V3 season workflow ("character bible → picks → wardrobe → voices → CAST LOCK"). It turns phase B's season demand list into individual "pick items" (faces, sheet views, expressions, outfits, appearance states, props, location masters with coverage plates, extras looks, neutral voice references, season music/SFX libraries), generates candidate images for them through a Nano Banana adapter that is fake by default and shares one cross-process file lock with the sibling ARISA system, and records operator votes as the only selection mechanism — generation happens solely through explicit operator actions (re-roll, generate next). It also adds a season-wide wardrobe plan with timed changes, a Botnoi voice catalogue with deterministic shortlists, audition records, casting sheets and a hardened upload intake for neutral reference clips, plus per-asset provenance records and automated output inspection. Everything freezes at a CAST LOCK gate that reuses the existing identity-lock tables (relaxed for V3 rows), stamps every episode row (fixing the R-12.1 bug), and blocks on forecast-over-cap, unapproved setup budget, unpicked or stale items, and incomplete provenance. All paid work flows through phase A's budget accounts under a step_04 setup sub-budget the operator approves before any spend. The build is sequenced as eleven packages (C1–C11), each landing with its acceptance tests green and its design note critiqued where money, locks, migrations or the trust boundary are involved.

**How the existing system works, per this document**

Today's V1/V2 system has reference asset versions that act as an implicit candidate grid but nothing records a choice; the identity lock is created only by the episode-1 Gate 2 approval, requires a source episode and release hash, and never attaches to episodes created later (the R-12.1 bug, with a dead attach helper); appearance states exist only as generic state events; the timed wardrobe resolvers exist but have no production caller and the render routing passes no state events; line-level TTS audio is ignored by rendering; and there is no Botnoi, picks, provenance-record or cross-system-lock machinery at all. Phase A supplies the gates, the decision transaction, jobs/queues, budget accounts and the UI shell; phase B supplies the story documents, the season demand list and a STORY LOCK hand-off whose forecast and image-volume panels are left NOT_AVAILABLE for C to fill. The document is written as a delta onto those specs plus a code fact map (c-factmap.md), using symbolic migration numbers C-1..C-8 that get real numbers once phases A and B land.
