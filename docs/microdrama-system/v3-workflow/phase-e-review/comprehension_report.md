**What this proposes**

Phase E is step 7 of the "V3" short-drama production pipeline: it turns the previous phase's accepted AI-generated video clips (which already carry their own generated audio) into a finished episode edit, replacing the legacy pipeline's behavior of discarding clip audio and laying separate TTS dialogue lines plus a whole-timeline room tone. It assembles a deterministic edit-decision list in which every clip contributes its embedded audio with synchronised A/V trims, uses generated room tone only in gaps between clips, renders fade/crossfade transitions in both the master and derivative exporters, and adds two new segments: a ≤10 s recap cut from the predecessor episode's approved source shots (which stays a typed pending-blocker until that predecessor's Gate 2 approval exists) and a ≤5 s call-to-action end card whose Thai copy is deterministically resolved from the current publication-calendar revision and never promises an unapproved extension. Captions are timed from measured utterance windows in the placed audio, with one Thai burned-in render plus per-locale subtitle tracks (th-TH, en-US, zh-CN) sharing the Thai timing; music and SFX are placed from the season libraries with a deterministic dialogue-ducking envelope, and per-episode SFX gap fills are the only paid work. Every released artifact is loudness-measured (ebur128) and normalised by a computed fixed gain to −14 LUFS ±1 / −1 dBTP with a hash-sealed per-artifact report, and a failing report is a typed blocker. Phase E deliberately has no approval gate of its own: it computes typed readiness blockers consumed by phase F's Gate 2 decision, registers deterministic rebuild triggers (predecessor approval, calendar revision, asset/library/text revisions) that always produce new versions and never mutate anything published, and exposes one operator verb (rebuild) plus an optional mix adjustment in a new tab-7 UI screen.

**How the existing system works, per this document**

The implementation plan (§13–§19) splits the work into eight sequential build packages — E1 migrations/document store, E2 the native-audio EDL and export graph, E3 captions, E4 loudness, E5 recap and CTA, E6 music/SFX cue sheets, E7 derivation checks plus the rebuild registration, E8 the tab-7 UI — each landing with named acceptance tests E-T1…E-T12 run fully offline against mocks (a fake utterance aligner, a fake SFX route, no network), with `make check` and the V1 pilot suite green at every package gate and four of the packages design-critiqued before building. The acceptance table claims to prove, per package: V1 edit tables byte-identical and still refusing V3 rows; clip-audio-only assembly with refused mid-word trims and gap-only room tone; three shared-timing caption locales with Thai-only burn; measured-gain loudness normalisation with typed failure instead of silent limiting; an approval-hash-bound recap and calendar-resolved CTA; constant-offset derivative synchronisation with byte-identical untouched units after a Revise-rebuild; provenance-gated cue sheets; metered SFX fills under the §10.5 crash-resume discipline; and registered rebuild edges that never touch published media. §15 keeps QA on the existing technical-check layers plus a provenance-completeness rule instead of re-inspecting pixels phase C already inspected, §16 logs six open questions each with a recommendation (burned-frame sampling, the exact ZH locale tag, D's word timings, C's library manifest shape, ownership of `MusicCue`/`SfxAsset`, per-locale hook tracks), §18 names the accepted risks (Thai alignment quality, Pika audio variance, ffmpeg drift, host CPU, recap serialisation, zh translation quality), and §19 records seven rejected alternatives with their reasons (new V3 tables, recap from the encoded master, recap bound to the live edit, burned EN/ZH variants, LLM-written CTA copy, single-pass loudnorm, full re-inspection).
