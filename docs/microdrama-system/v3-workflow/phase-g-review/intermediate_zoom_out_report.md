### S8-Z-1. No authoritative home for G's durable records — the "survive the ephemeral profile" invariant is stated once and never generalized - Severity: Major
* **Reviewer Lens:** `egm-zoom-out` (instance B primary; instance A concurring in altitude assessment and §15-omission item)
* **Affected Scope:** §2 (lines 130-155), decision 3 (lines 74-80), decision 9, §7.1 (lines 344-350), §7.2 item 1 (lines 356-359), §10 `record_live_claim` (line 446)
* **Discrepancy Description**: The four document types have three plausible database homes and only `ProductionCompositionV3`'s is unambiguous. The pilot profile has its own DB (decision 3) following a drill pattern that ends `down -v` (drill.sh:141, verified); `PilotRunV3` and the measured landing refs therefore live in a teardown-destined DB; `RestoreProofV3` is written by a drill that restores into a fresh scratch project (also `down -v`); and the spec never says which store `record_live_claim` writes to, nor whether pilot evidence is exported to the committed `microdrama/evidence/pilot/` files (named in §2 with no writer or cadence). Decision 9 states the exact principle needed — durable records must survive ephemeral databases — but applies it only to the all-gates artifact. Two further instances: P0's calibration results "feed C's forecast config" (a pilot-DB measurement feeding a production config with no stated bridge), and P2's release legs create permanent external effects (real published posts, real spend receipts) whose local provenance — slot identities, dedupe keys — is scheduled for destruction at teardown.
* **Rationale & Recommendation**: This is the systemic root under prior S5-Z-2 and S7-2, and the strongest whole-holds-together question in the design: qualification artifacts and real-world side effects originate in homes designed to be destroyed. It is a scope omission with a local-size fix: add one rule in §2 (any record produced in an ephemeral or teardown-destined profile references committed, sha256-bound file artifacts; the authoritative `v3_ops_documents` for LIVE claims and activation is the production store), plus a named export-at-phase-close step and a retention-then-teardown runbook step (teardown only after the §11/LIVE sign-off). One section edit; no redesign.

### S8-Z-2. The AT-14 alert machinery is placed in a new always-on 60-second poller — over-machinery whose placement is unrecorded, and the source of the durable-edge problem - Severity: Major
* **Reviewer Lens:** `egm-zoom-out` (instance A primary, instance B concurring — found independently by both)
* **Affected Scope:** §2.1 GD1 (lines 159-163), §4 (lines 232-254, alert bullet 247-251), decision 1 (lines 63-65), §10 schedules line (line 451), §11 G2 row (line 465)
* **Discrepancy Description**: G's only new runtime mechanism is a new `g.quota_pause` schedule at a 60 s interval whose sole job is rising-edge detection for one alert — the pause itself is the existing A0 §5.7 dispatch gate, and the predicate's inputs (quota observations, PACE_WEEK deferrals) change only when jobs attempt. The 60 s cadence is 3-5x faster than anything in the schedule catalog (verified: fastest existing interval is 5 minutes, registry.py:129/:135), introduces a new cadence class into the scheduler, requires the GD1 crossing registration, and then creates the exact problem two prior stages rated Major: a derived, never-stored (AR-4) predicate needs durable episode memory that no existing surface provides (firing identity is the tick bucket, registry.py:59; A §8.4 has no wait-ended event, verified). The edge it polls for is already known at the moment the dispatch gate engages the route pause — that refusal *is* the rising edge — and the outbox's at-least-once/consumer-dedupe semantics (S/core/events.py:8-10) would carry an episode-keyed idempotent event emitted there, deleting the schedule, the crossing, the restart-edge reconstruction, and the S7-1 retry-gap false-edge hazard in one design choice. Alert latency under the alternative is bounded by A0's own retry cadence (~+10 min for QUOTA_UNREADABLE per FM §3), and no master text specifies alert latency. The alternative has its own cost (workers are many; the scheduler singleton is one), so this is a genuine architectural choice — but the spec makes it silently and §16 has no rejected-alternative row for it.
* **Rationale & Recommendation**: Prior stages tried to complete the mechanism ("where does the edge sample live") without questioning the host. Either (a) emit the scope-level GD2 event at pause engagement/recovery in the gate path, with episode identity as the event idempotency key, or (b) keep the poller and justify in §4 why sub-retry-interval detection is worth a permanent new schedule — in which case the G2 note must pin durable episode identity per S7-1(a)-(c). Either way, record the choice and its reason in §4, add a §16 row, and resolve S7-1(c)'s track scope (`track='production'`-only event vs route-level pause) here, since the event-driven shape makes the track question unavoidable.
