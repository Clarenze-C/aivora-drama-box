## M1 validation round 3 (independent, /tmp probes)

- Probe: 49 passed, 2 findings + notes.
  - V-37 (MAJOR): the round-2 "non-human bearers refused before the body is parsed" invariant
    does not hold for bodies that fail JSON decoding — FastAPI decodes the body before
    dependencies run, so a service/webhook bearer with malformed JSON gets 422 SCHEMA_INVALID,
    not 403 (all four non-human kinds). Bodies are also fully buffered before the refusal.
    Fix: refuse the principal in middleware/custom APIRoute before body handling.
  - V-38 (MINOR): the pre-session double-submit token is never consumed server-side — replay of
    the same (cookie, form) pair after successful sign-in mints another session; the 15-minute TTL
    exists only in the cookie; after a wrong password the renewed token does not invalidate the
    old pair. Bounded impact (pair alone is worthless), defense-in-depth gap.
  - NOTEs: no per-owner scoping (any human owner reads any episode — consistent with the
    single-operator model); stale binding surfaces as 409 STALE_REVISION before blocker
    evaluation (fresh-key-proof); a second REVISE out of a repair stage is refused (matches the
    documented loop); FilesystemObjectStore put_bytes is tamper-resistant (content-addressed,
    Conflict on divergent overwrite).
- Round-3 fixes (review lane): V-37 a route-level guard (`_refuse_non_human_route`, custom
  APIRoute) refuses non-human bearers on every human-only route from the Authorization header
  alone, before FastAPI reads or decodes the body — malformed/huge bodies with a service bearer
  are 403, junk bearer stays 401, human+malformed stays 422. V-38 migration 0014 `login_tokens`
  stores sign-in double-submit tokens as SHA-256 digests; redemption is a single atomic
  conditional UPDATE (single-use under races), TTL is server-clock, a failed attempt burns the
  token and the fresh one invalidates the pair, and a mismatched pair does not consume the
  browser's real token. Review suites 221 passed; persistence suites 123 passed (0014 applies,
  schema-catalog guards cover it); all 6 probe xfails → XPASS.
  NOTEs: login_tokens rows are never deleted (bounded by page views; cleanup is an integrator
  decision); the guard selects human routes by the endpoint's `principal` parameter name — new
  human routes using a different name fall back to the post-parse dependency backstop.

- Round-4 verification (integrator): probe suite 49 passed + 6 XPASS; make check green
