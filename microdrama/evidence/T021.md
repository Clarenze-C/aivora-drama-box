## Acceptance evidence (task_breakdown §5 T021 row)

- **Implements the common T020 interface without local alternate approval/budget
  logic**: `YouTubeAdapter` implements exactly `capability / submit / status /
  reconcile / update_metadata / readback` (protocol conformance pinned in
  `test_youtube_adapter_satisfies_the_frozen_publisher_protocol`); every gate
  (approval binding, media pinning, capability pinning, disclosure support,
  dependencies, attempt caps) stays in `PublishingService` — the adapter only
  maps platform rules and transport outcomes.
- **Full vs Shorts routing**: route is decided from the slot kind alone
  (`FULL_EPISODE`/`PART` → long-form video, `PROMO_CUT`/`HOOK` → Shorts) plus the
  capability record; both routes ride the same documented `videos.insert`
  surface, and the Shorts duration/aspect contract lives in the capability
  snapshot (`RESEARCH_LIMITS` + evidence notes), never inferred by probing media
  (`test_long_form_and_shorts_route_from_slot_kind`,
  `test_shorts_slot_publishes_through_the_service`). A route whose upload
  operation is not supported refuses that route only
  (`test_unsupported_route_operation_refuses_that_route_only`).
- **Resumable upload / status / reconcile**: the transport models the documented
  resumable protocol (metadata on the initiating request → session URI → media
  PUT returning the video id). Status maps the documented `uploadStatus` ladder
  (uploaded → processing → processed) to SUBMITTED → PROCESSING →
  PUBLISHED_VERIFIED; reconcile/dedupe is by `client_token`
  (`test_status_progression_is_submitted_processing_verified`,
  `test_timeout_created_is_reconcilable_by_client_token`).
- **Schedule**: future windows use the documented private + `status.publishAt`
  model — the video exists privately and turns public at the instant (fake
  clock), verified end-to-end through the service
  (`test_future_schedule_uses_private_publishat_then_turns_public`,
  `test_schedule_ahead_flows_private_then_public_through_the_service`);
  without SCHEDULE support the adapter refuses
  (`test_future_schedule_without_schedule_support_is_refused`) and the T020
  service's own denial is pinned too
  (`test_schedule_ahead_without_schedule_support_is_denied`).
- **Synthetic declaration**: AI_GENERATED_CONTENT (and SYNTHETIC_VOICE riding the
  same documented field — there is no separate voice declaration) maps to the
  altered-content/synthetic-media field; readback proves it visible
  (`disclosures_visible`), and any disclosure without a documented field is
  refused/HELd, never silently dropped
  (`test_unsupported_disclosure_is_refused_before_any_upload`,
  `test_unsupported_disclosure_holds_the_slot`).
- **Captions/localizations**: present as documented capability operations
  (CAPTIONS_UPLOAD via `captions.insert`, LOCALIZED_METADATA via the

  implements no linking of its own.

## Implementation limits and honest unknowns

- **No live transport exists.** `LiveYouTubeTransport` is a named refusal; every
  result this lane produces is `Provenance.FAKE_SYNTHETIC` with `*.invalid` URLs
  and stable-digest ids, driven by a scenario queue mirroring the T007 fakes.
- **Documentation URLs and figures were snapshotted from official documentation
  as of 2026-10 from the implementer's knowledge; they were NOT re-fetched during
  this task (offline network guard is active by design).** In particular the two
  support-article ids (altered-content answer `14334423`, Shorts answer
  `10059070`) and the exact field name of the altered-content flag
  (`contain_synthetic_media` in this snapshot) must be re-verified against the
  live docs at T031/T032 qualification; the mapping is isolated in
  `capabilities.DISCLOSURE_FIELD_MAP` / the transport's `VideoStatus` so a
  correction is a one-line snapshot change, not a redesign.
- Fixture upload processing advances one documented step per `videos_list` call
  (deterministic approximation of server-side transcoding time), and the
  scheduled-public transition is evaluated against the fake clock. A live
  transport will report true time-based state instead; the adapter's mapping
  (processed + public window ⇒ PUBLISHED_VERIFIED, else PROCESSING) is unchanged.
- `update_metadata` maps title/description/tags; YouTube has no separate hashtag
  field (hashtags are a description convention), so `metadata.hashtags` ride
  `snippet.tags` unchanged and no description text is ever rewritten by the
  adapter.
- The readback reports the single altered-content field as covering BOTH mapped
  disclosure kinds when set; a future separate synthetic-voice surface (none
  documented today) would need its own mapping.
- `INSIGHTS` etc. stay UNKNOWN rather than documented because this snapshot only
  researched the publishing surface; the owning lanes (T025/T027) snapshot their
  own operations.
