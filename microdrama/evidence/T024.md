## Acceptance evidence (task_breakdown §5 T024)

- **Explicit short-Reel vs supported full-video route, no inference**: route is
  chosen strictly from `slot_kind` (`_ROUTE_BY_KIND`): FULL_EPISODE/PART → the Page
  videos edge (resumable chunks then finish, `fb-full-*` ids), PROMO_CUT/HOOK → the
  Reels container flow (start/upload/publish, `fb-reel-*` ids). Tests pin that a
  full submit NEVER touches `start_reel_container`/`publish_reel` and a reel submit
  NEVER touches `start_page_video_upload`/`finish_page_video_upload`
  (`test_routes_and_rules.py::TestExplicitRouteSelection`, contract
  `test_explicit_route_selection_full_and_short`); the resumable protocol
  (contiguous chunk offsets, finish only after every chunk) is pinned in
  `test_resumable_upload_transfers_contiguous_chunks_then_finishes`.
- **No speculative capability for long video**: with the test-only
  `NO_FULL_VIDEO_OPS` variant the adapter refuses before any transport call
  (`test_upload_operation_not_supported_is_a_policy_refusal`) and the SERVICE HELDs
  a FULL_EPISODE slot with `CAPABILITY_UNAVAILABLE`
  (`test_unknown_full_video_holds_full_episode_slots`). In the shipped snapshot
  UPLOAD_FULL_VIDEO IS documented (videos edge), so FULL_EPISODE is not held for
  capability reasons — it is held for the disclosure reason below.
- **Page scope**: `capability()` returns `account_type='page'` records and REFUSES
  unknown/user-timeline accounts with PolicyDenied ("personal profiles have no
  publishing API") —
  `test_capability_refuses_user_timeline_accounts`. All fixture publishing runs as
  the mock Page `acct:facebook-main`.
- **Upload → processing → published (+ scheduled publish where documented)**: the
  fixture models the documented lifecycle `uploaded → processing → published`, one
  phase per status call, with `scheduled_publish_time` honored ONLY on the videos
  edge: a scheduled full video stays PROCESSING until its window opens and only
  then publishes (`test_future_window_full_video_uses_the_documented_schedule`,
  service `test_scheduled_full_video_publishes_only_at_its_window`, contract
  `test_scheduled_full_video_verifies_only_after_its_window`). A future-window
  SHORT slot is FAILED `SCHEDULE_UNSUPPORTED_ON_REELS` — the Reels surface
  documents no schedule parameter, so it is never silently published early
  (`test_future_window_short_slot_is_refused` + service-level equivalent); with
  SCHEDULE withdrawn the full route also refuses (`SCHEDULE_UNSUPPORTED`).
- **Disclosure/readback declaration truth (the documented outcome)**: no documented
  Graph API field sets AND reads back an AI label for organic Page video posts
  (snapshot 2026-10) → `AI_DISCLOSURE=UNKNOWN`, `supported_disclosures=[]` on BOTH
  the default and the fixture record (the evidence label differs; the platform
  truth does not). Because MD-015 requires `AI_GENERATED_CONTENT` on EVERY slot,
  every Facebook slot HELDs with `UNSUPPORTED_DISCLOSURE` through the service —
  pinned as the documented outcome (`test_declaration_truth_holds_every_ai_disclosed_slot`,
  unit `test_ai_disclosed_slot_holds_unsupported_disclosure`), held stays held until
  the destination changes (`test_held_slot_stays_held_until_the_destination_changes`),
  and even a published video's readback reports `disclosures_visible=[]` with
  `'disclosures'` in `unverified_fields`
  (`test_published_video_cannot_prove_the_ai_label`). The adapter additionally
  refuses AI-disclosed submits itself (FAILED `DISCLOSURE_UNVERIFIED`) as defense
  in depth. This changes only if Meta documents such a field or T032 measures one.
- **Where the encoding allows, the full verify flow runs**: with the TEST-ONLY
  `TEST_AI_CAPABLE_OPS` variant (a Page surface that can set+read the label — a
  test parameter in the `FakePublisherAdapter` tradition, NEVER a shipped
  capability), the complete pipeline runs offline through the REAL service:
  schedule → submit → SUBMITTED (`fb-full-*`) → poll → PROCESSING → poll →
  readback-gated PUBLISHED_VERIFIED (`https://facebook.invalid/...` URLs only) →
  `release_view` ready → episode PUBLISHED_VERIFIED
  (`test_full_offline_release_flow_schedule_to_verified`, unit
  `test_schedule_to_verified_full_release`), including the optional PROMO_CUT on
  the reel route alongside the required full slot
  (`test_optional_hook_runs_the_reel_route_alongside_the_full_episode`).
- **Frozen scenario matrix through the service**: ACCEPTED→SUBMITTED,
  DENIED_PERMISSION/TOKEN_EXPIRED→FAILED, RATE_LIMITED→RETRY_WAIT (retry_after_ms
  60 000, nothing created), TIMEOUT_CREATED/TIMEOUT_NOT_CREATED→
  NEEDS_RECONCILIATION — contract
  `test_provider_response_matrix_maps_to_slot_states` (parametrized 6×, each path
  leaving exactly ONE durable provider operation, job-linked, `reservation_id`
  NULL i.e. unmetered per contract 1.6.0, provider `facebook-page`).
- **Replayed submit dedupe by client_token**: two job runs → one provider
  operation row, one post at the platform, same external id, and the replayed
  answer does not advance the platform lifecycle (reconcile/peek vs status/poll)
  — contract `test_replayed_submit_is_deduplicated_by_client_token`, unit
  `test_replayed_submit_is_deduplicated_by_client_token`.
- **Crash safety through the service**: TIMEOUT_CREATED lands in
  NEEDS_RECONCILIATION, blind resubmit refused, reconcile ADOPTS the found post by
  client token and polls to PUBLISHED_VERIFIED completing the episode;

## Implementation limits and honest unknowns

- **Live publishing is NOT implemented** — there is no HTTP transport. Outside
  OFFLINE_MOCK the factory wires `RefusingFacebookTransport` (every call raises
  `PolicyDenied("live publishing disabled until T032")`) and the disabled
  documentation snapshot (`enabled=False`); the fixture branch is guarded by
  `ensure_mock_mode`. Tests autouse the offline network guard; nothing in this
  lane can reach the network.
- **AI_DISCLOSURE = UNKNOWN is an honest unknown, not a refusal claim**: Meta may
  apply AI labels via its own detection or creator-tool surfaces; the snapshot
  found no organic-Page-post Graph API field the pipeline can SET and READ BACK.
  Until that changes (docs update or T032 controlled test), every Facebook slot
  HELDs UNSUPPORTED_DISCLOSURE by design.
- **CapabilityLimits is a single box for a two-route record**: it carries the
  documented REEL ceilings (0.5–90 s, 9:16) as the packet prescribes; the
  full-video route's separate (larger) documented ceilings are NOT expressible in
  contract 1.6.0. Nothing in the publishing service enforces limits today, but any
  future consumer applying `max_duration_ms` to a FULL_EPISODE slot would
  mis-apply the reel ceiling. **Proposal for the integrator (no contract change
  made):** route-scoped limits (e.g. `limits_by_route` or per-operation limits) in
  a future additive contract bump.
- **Reel limits are a documentation snapshot** (duration floor/ceiling, aspect)
  and were not measured against a live account; T032 must confirm them before any
  live encode. Full-video file-size/codec ceilings were not encoded (uncertain
  numbers are left out rather than guessed).
- **Test-only capability variants** (`TEST_AI_CAPABLE_OPS` etc. in
  `facebook_support.py` / the contract module) exist solely so the matrix and the
  verify flow can run through the service; they are constructor parameters of the
  adapter (the same pattern as `FakePublisherAdapter(operations=...)`), never the
  shipped default, and are loudly labelled in both modules.
- **Reels scheduling**: the refusing behavior encodes "no documented
  scheduled-publish parameter on the Reels surface" (snapshot 2026-10). If Meta
  documents one, SCHEDULE handling for the short route is a snapshot update, not a
  code redesign.
- **update_metadata** covers the documented title/description edits; the fixture
  readback does not model privacy or subtitle fields (they stay in
  `unverified_fields` — honest UNKNOWN, matching the reference adapter).
